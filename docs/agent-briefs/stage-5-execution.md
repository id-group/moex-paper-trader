# Бриф этапа 5: Модель исполнения ордеров

## Цель

Реалистичное виртуальное исполнение: матчинг маркет/лимит ордеров по стакану и потоку сделок,
модель проскальзывания (точно по спецификации), контроль ликвидности, частичные исполнения,
жизненный цикл ордеров. Замена заглушки этапа 2/3 на `MatchingEngine`.

## Прочитать до начала

1. `AGENTS.md` — принцип №6 (модель проскальзывания — НЕ упрощать без согласия владельца).
2. `docs/ARCHITECTURE.md` — раздел 7 (ADR-9).
3. Код `core/execution` (порт), `core/marketdata` (стакан/сделки/ADV), `core/portfolio`
   (комиссии, блокировки), `bks/adapter` (как ордера попадают в core).

## Скоуп

- `core/execution`:
  - `MatchingEngine`: прием ордеров из adapter'а; маркет — немедленный кросс стакана;
    лимит — постановка в очередь, исполнение при пересечении рынка (buy: ask ≤ limit,
    цена = min(limit, bestAsk); sell — симметрично), частичные исполнения по прошедшему объёму.
  - `SlippageModel` (интерфейс + дефолт по спеке): базовый случайный компонент 0.05–0.15%
    в неблагоприятную сторону + тир по размеру ордера относительно ADV: <1% → +0.05%,
    1–5% → +0.1%, >5% → +0.2%. Seed — из `Clock`/конфига (детерминизм в REPLAY).
  - `LiquidityPolicy`: порог (дефолт 5% ADV, настраивается на профиль брокера); превышение →
    reject с кодом ошибки контракта БКС (согласовать: RESOURCE_EXHAUSTED/CONFLICT — см.
    ErrorResponse enum в `docs/bcs-api/http/portfolio.md`) ИЛИ разбивка на части (политика
    настраивается: REJECT | SPLIT).
  - Жизненный цикл ордеров: NEW → PARTIALLY_FILLED → FILLED / CANCELLED / REJECTED;
    лог переходов в `order_events`; cancel/edit — через порт (edit = cancel+create, как у БКС).
  - Таймаут лимиток: timeInForce Day (снятие в конце сессии), FOK, GTD (expiryDate) — по
    контракту create.RequestSchema.json.
- Проводка сделки в портфель: Fill (цена после проскальзывания, комиссия) → `core/portfolio`.
- Режим REPLAY: матчинг детерминирован (Clock + seed), лимитки исполняются по истории
  сделок/стакана записи.

## Явно НЕ делать

- Симуляцию очереди заявок по позиции в стакане (зафиксировано допущение «исполнение при
  пересечении цены»); стоп-лоссы/условные ордера (orderType 3–5 контракта — заглушка
  NOT_IMPLEMENTED с явной ошибкой, TODO в коде); WebSocket-нотификации.

## Обязательные тесты (критичный компонент — максимальное покрытие)

- Маркет: buy исполняется по ask+слиппедж; sell — по bid−слиппедж; тиры ADV (0.9%/2%/6% →
  0.05/0.1/0.2% + базовый компонент в границах 0.05–0.15%) — границы проверить стохастически
  (много прогонов с фиксированным seed).
- Лимит: не дошёл — ждёт; дошёл — исполнен по «лимит или лучше»; частичное исполнение;
  отмена; Day-снятие в клиринг; FOK отклонён при нехватке объёма.
- Ликвидность: 6% ADV → reject (REJECT-политика) / серия частей (SPLIT-политика).
- Детерминизм REPLAY: два identical прогона → identical fills.
- Интеграция: create order (через HTTP БКС) → fill → портфель/журнал обновились.

## Definition of Done

- `./gradlew clean build` зелёный; все тесты проскальзывания/ликвидности проходят;
  спецификация модели соответствует принципу №6 AGENTS.md покамерно (таблица в отчёте).

## Подводные камни

- Проскальзывание — в неблагоприятную сторону для клиента (buy дороже, sell дешевле).
- Не смешивать: комиссия (в Fill) и проскальзывание (в цене) — разные поля журнала.
- `Random` только через инжектируемый seed-источник; в LIVE — `SecureRandom`/системный seed.
- Файлы — UTF-8 без BOM.

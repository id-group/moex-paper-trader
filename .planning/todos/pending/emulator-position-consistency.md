## P1 (критично) — `positions.quantity` не равна сумме исполнений по инструменту

Факт по данным прогона:

| инструмент | сумма `fills.quantity` | `orders.executed_quantity` (сумма по заявкам) | `positions.quantity` |
|---|---|---|---|
| 1 (HYDR) | 272 975 | 272 975 (заявка 7 FILLED) | **12 745** |
| 2 (FEES) | 67 564 | 67 564 (заявка 8: 67 564 из 2 152 698, CANCELED) | **32 273** |
| 4 (AFLT) | 3 818 | 3 818 | **2 184** |
| 3 / 5 / 6 | 20 862 / 8 467 / 1 282 | то же | совпадает |

Инвариант, который должен выполняться всегда:

```
positions.quantity(account, instrument) == sum(fills.quantity) - sum(исполнения на продажу)
```

Наблюдается только для инструментов, по которым в прогоне была одна активная заявка
(3, 5, 6). Там, где по одному инструменту шли **две перекрывающиеся заявки** (1: заявки 1+7;
2: заявки 2+8) или заявка исполнялась параллельно с тиком по другой заявке того же
инструмента — позиция меньше фактических исполнений.

Подозрение (проверить, не принимать как диагноз): в `FillServiceImpl.fillInternal` на каждое
исполнение портфель целиком пересобирается из БД (`restorePortfolio`), а затем `persist`
пишет позицию абсолютным `upsert ... SET quantity = EXCLUDED.quantity`
(`PositionRepository.upsert`). Если две транзакции исполнения по одному инструменту
пересекаются, вторая теряет первую (lost update): ни блокировки строки позиции, ни
оптимистичной версии нет — `lockAccount` защищает только `account_balances`.

Что сделать:
1. Написать интеграционный тест, воспроизводящий потерянное обновление: две активные заявки
   BUY на один инструмент, исполнения применяются параллельно (или вперемешку с
   `ExecutionService.tick()`), после чего проверить `positions.quantity == сумма fills`.
   Сейчас тест должен падать.
2. Выбрать и зафиксировать один из вариантов:
   - сериализация изменений позиции (блокировка строки `positions` по
     `account_id, instrument_id` так же, как блокируется счёт);
   - инкрементальный `UPDATE positions SET quantity = quantity + :delta` вместо абсолютного
     upsert (плюс отдельный путь сокращения/удаления позиции);
   - оптимистичная блокировка (`@Version`) с ретраем транзакции.
   Обоснование выбора — в комментарии/ADR, если оно не очевидно.
3. Проверить `account_balances.cash`: после фикса сверить, что
   `start_cash - sum(price*quantity + commission)` совпадает с `cash` (в прогоне
   `cash = 454 455.44`, суммарный notionал по всем фишлам — 594 677.84; убедиться, что
   расхождения нет или оно объяснимо комиссией/округлением).
4. Добавить постоянный инвариант-тест (или SQL-проверку в тесте): для любого состояния БД
   позиция = сумма неискупленных исполнений.

## P2 (критично) — `positions.average_price` = цена последнего фишла, а не средневзвешенная

FEES (инструмент 2): цены исполнений в стакане чередуются 0.06960 / 0.06964 / 0.06966 /
0.06968, доля каждого разная. В БД `average_price = 0.069680` — в точности цена последнего
фишла. Для HYDR `average_price = 0.549412` при 1 347 фишлах — тоже проверить.

Что сделать:
1. Тест: последовательность BUY-исполнений по разным ценам → `average_price` равна
   `sum(q_i * p_i) / sum(q_i)` с учётом округления, принятого в `Money`/`PortfolioPosition`.
2. Гипотеза для проверки: при каждом `fillInternal` портфель восстанавливается из строки
   `positions`, а `averagePrice` в `VirtualPortfolio.buy` при частично исполненной позиции
   перезаписывается вместо перевзвешивания; либо абсолютный upsert (см. P1) пишет значение,
   посчитанное от устаревшего снимка. После фикса P1 убедиться, что цена тоже сходится.
3. Отдельно проверить случай сокращения позиции (SELL): средняя остаётся неизменной,
   реализованный P&L не должен её менять.

## P3 (высокий) — заявки DAY отменяются «до истечения дня» и исполнения идут вне сессии

Хронология прогона (UTC):

```
торговая сессия TQBR 2026-11-13 по trading_calendar: 07:00 – 15:50
16:01:52–16:01:56  созданы заявки 1–6 (BUY)
16:01:54–16:01:56  те же заявки → EXPIRED / CANCELED, reason "Срок действия заявки истёк"
                   (executed_quantity = 0, фишла нет)
16:11:07–17:02:21  заявки 7–12 исполняются (2 480 фишла) — то есть вне календарного окна
```

`ExecutionServiceImpl.isExpired` для `DAY` возвращает `!session.open()`, и `tick()`
сразу экспайрит такие заявки. Отсюда два вопроса, оба требуют решения «как правильно для
эмулятора БКС»:

1. **Открытие заявки вне сессии.** Реальный брокер принимает DAY-заявку вне основной сессии
   (на следующую сессию / в период аукциона), а не отменяет её в течение секунды с тем же
   текстом причины. Текущее поведение ломает тестовые прогоны: сигнал, пришедший вечером,
   умирает мгновенно.
2. **Исполнение вне календарного окна.** Если сессия «закрыта» по `trading_calendar`, но
   `MarketDataProvider.tradingSession()` (LIVE: `AlgoPackMarketDataProvider` /
   `IssMarketDataProvider`, обёрнутые в `FallbackMarketDataProvider`) считает её открытой —
   два источника истины о сессии расходятся. В прогоне фишла шли 2–3 часа после
   `close_utc`. Нужно выбрать один источник и сверить с ним экспирацию.

Что сделать:
1. Вывести в тест явные сценарии: (а) создание DAY-заявки до открытия сессии, (б) после
   закрытия, (в) во время клиринга; ожидаемое состояние заявки и причина.
2. Сверить `isExpired(DAY)`: экспирация должна происходить на границе дня/клиринга по тому же
   источнику сессии, по которому движок разрешает исполнения, а не по «сейчас сессия
   закрыта».
3. Добавить в `EXPIRED`-событие различимую причину с таймстемпом источника сессии — иначе
   при разборе прогонов невозможно отделить «день закончился» от «календарь не совпал».

## P4 (средний) — семантика `order_events.quantity` в терминальных событиях

Текущие значения из прогона:

- `PARTIALLY_FILLED` → `quantity` = размер отдельного фишла (например 2, 7, 92);
- `FILLED` (заявка 10) → `quantity = 41`, тогда как `orders.executed_quantity = 3 818`;
- `EXPIRED` (заявка 8) → `quantity = 2 085 134` — это **неисполненный остаток**, при том что
  `executed_quantity = 67 564`.

То есть в одной колонке смешаны «размер события», «итог по заявке» и «остаток». Для аудита
и для внешних потребителей (trading-service читает статусы через БКС-контракт) это источник
ошибок интерпретации.

Что сделать:
1. Зафиксировать договорённость в docs (`docs/bcs-api/**` или внутренний документ о
   событиях): что именно означает `order_events.quantity` для каждого `event_type`.
2. Привести реализацию к договорённости — рекомендовано: в терминальных событиях
   (`FILLED`, `CANCELED`, `EXPIRED`, `REJECTED`) писать накопленный `executed_quantity`,
   размер последнего фишла оставлять в `PARTIALLY_FILLED`.
3. Тест на каждый терминальный тип.

## Репродукция данных прогона (запросы к `papertrader-local-postgres`)

```sql
-- дисбаланс позиций и исполнений (P1)
select o.instrument_id,
       sum(f.q)                        as fills_qty,
       sum(o.executed_quantity)        as orders_exec,
       max(p.quantity)                 as position_qty
from orders o
join lateral (select quantity as q from fills where order_id = o.order_id) f on true
left join positions p on p.account_id = o.account_id and p.instrument_id = o.instrument_id
group by o.instrument_id;

-- средняя цена против средневзвешенной (P2)
select instrument_id,
       round(sum(price * quantity) / sum(quantity), 6) as vwap,
       max(executed_at)                                as last_fill
from fills group by instrument_id;

-- хронология экспираций и сессии (P3)
select order_id, event_type, status, quantity, reason, occurred_at
from order_events where event_type <> 'PARTIALLY_FILLED' order by occurred_at;
select trade_date, open_utc, close_utc from trading_calendar where trade_date = date '2026-11-13';
select min(executed_at), max(executed_at), count(*) from fills;

-- терминальные события (P4)
select order_id, event_type, status, quantity, occurred_at
from order_events
where order_id = '20261113-TQBR-796285400008' and event_type = 'EXPIRED';
select order_id, executed_quantity from orders where order_id = '20261113-TQBR-796285400008';
```

Ключевые артефакты прогона: заявка `20261113-TQBR-796285400008` (FEES, `quantity=2 152 698`,
`executed_quantity=67 564`, `CANCELED` с причиной «Срок действия заявки истёк» в 17:02:22 UTC)
и её 753 фишла в окне 16:28:18 → 17:02:21 UTC.
